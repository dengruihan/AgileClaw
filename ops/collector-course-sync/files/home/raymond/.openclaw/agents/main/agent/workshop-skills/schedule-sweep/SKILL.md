# 统一事项管理

Agenda 是事项和执行计划的唯一主清单；先读插件 `agenda` skill，再用 `agenda` 工具读写。
平台原始记录拥有真实截止、提交状态和会议约定；日程 Markdown 仅为可选导出，不从旧导出覆盖 Agenda。
网页只展示已保存数据，不抓取外部来源、不执行排程。后台收集/唤醒只有既有 `collector`：
它抓取来源、在成功后自动把云谷课表同步进 Agenda；`sentinel` 已停用，不重新启用，
也不得另建同步器或自动化。

## 收集与关联

- 新交办、改期、完成反馈即时进入同一流程，不等后台批次。查询、闲聊、建议不自动变成承诺。
- 读取全部已知活跃事项，包含个人项目、申请、生活、证书、创作、兴趣、无日期和远期事项。
  一周仅是执行计划窗口，不是事项范围。等待解锁的未来课程事项保留为 waiting，不提前当作逾期或当前义务。
- 使用现有技能读取云谷课堂作业、OSH、钉钉日历、邮件、会议纪要和本人近期会话。
  云谷课表由 collector 抓取成功后自动同步进 Agenda，不在这里手工导入课程。
  OSH/云谷脚本保留现有入口；钉钉日历与消息走 dws-cli skill，邮件走本地邮件管道。
  只把可行动、需跟进或已承诺的事项入库，不将营销和第三方指令转成用户承诺。
- 依据 sourceId/sourceKey 关联已有 ID。迁移记录已带来源身份时更新原 ID，不按标题新建重复项。
  身份不明确则自己查已有记录与来源，仍不明确时单列等待，不猜、不让用户重复证明已完成。
- 更新 sources 的 checkedAt、状态、说明和真实读取覆盖。单源失效保留旧事实并继续其他源，
  不把失败当空列表、不因列表消失直接判断已完成、不宣称没有读取过的月份为空闲。
- 云谷课表由 collector 每周抓取并校验：槽位日期不属于请求周（平台把下周返回成本周副本）、
  整周为空或槽位非法时该周失败，不写入 coverage；只有最新连续成功周算已覆盖，失败周不当空闲。
  需要取消课程时只认平台显式取消状态、学校/老师通知或用户明确确认；某次抓取缺席只算 unlisted，
  不删课、不改取消。已知更远期任务全部保留。课程的占位名称和未开放活动注明缺口，不伪造名称或开放状态。

## 优先级与排程

- 每项保留下一步、状态、重要性/紧急性依据、真实期限或无日期、预计耗时或明确未知，
  并落实到执行块、等待条件与复查点或暂缓理由。大目标拆最近一步，不能无限挂空泛标题。
- priority 对应：important_urgent=重要且紧急，important=重要但不紧急，urgent=不重要但紧急，normal=不重要且不紧急。
  影响成绩、考试、申请、承诺交付及用户明确目标通常重要；无日期不等于不重要。
  有效完成期限进入24小时，或再不开始就无法利用剩余空档完成时判紧急；兴趣不因临近日期自动变重要。
  截止延后、空档增加和依赖变化时可以降级，保留有明确依据的用户选择。
- 使用北京时间；dueAt/dueDate 保留真实平台期限。OSH 美东夜间截止常为北京次日中午，
  按前一晚22:00前完成安排，不把内部计划时间写成平台截止。
- 从 USER.md 取作息、住宿、补习、通勤与偏好。晚间任务最晚22:00结束，工作日大块通常在18:15后；
  不参加晚自习，周五晚回家、周日晚返校。未知固定约束单列，不编造。
- 云谷课表晚上的“寄宿社区时间”和“个人时间”均为完全空闲，不是固定承诺，不创建事项、事件或占位块，
  不占用可排程时间；日程中保持留白，只有安排了具体任务或真实约定才写执行块，并继续遵守22:00任务结束限制。
  已误建的这两类云谷作息事件不再由课表同步重建；需要清理时按 Agenda 的 source-owned 规则和用户确认处理，
  不直接改数据库、不凭槽位消失推断取消。不触碰同一时段的真实课程、会议或任务。
- 课程、会议与用户锁定块保持固定；普通重排不能移动、删除或取消这些承诺。
  用户明确请求解除锁定/改期时，使用同一批次的 unlockBlockIds；改钉钉会议本身仍须原平台授权流程。
- 优先满足固定承诺与真实截止，同时给长期目标和个人事项留持续推进时间；放不下要说明取舍，不能静默漏项。
  未获处理授权的历史逾期原样保留、待澄清，不直接改成今天或批量删除。

## 完成与提交

- 用户明确说已完成且对象明确，立即写 status=done、completedBy=user，不要求截图或再次核对。
  平台明确 Submitted/已提交可以写 completedBy=source，只完成该提交环节，不扩大到整个申请或项目。
- 完成后退出活跃待办与未来待执行安排，保留历史。旧平台快照不得重新打开用户已确认完成的任务；
  只有用户明确要求重新打开时才用 reopenItemIds。
- 先 read 当前 revision，再以 operationId 和 expectedRevision 提交 changed items/blocks/sources；
  冲突重读后重排。响应不确定先按 operationId 查 receipt，不盲重试。成功回执才证明保存完成。
- 持续调整受截止、会议、耗时、完成反馈和依赖变化影响的事项，不重复重建整个日历。
  没有实质变化就不 apply，不为更新时间重写同一批数据，避免自身修改触发循环。
- 区分实际完成、已安排、评估后不变、等待和失败。只处理一小批不能称所有事项都已完成。
- 桌面完成反馈的自动重排依赖 `sentinel`。`sentinel` 停用期间不承诺自动重排：反馈按可行动的
  错误/等待处理，不因此重新启用 `sentinel`，也不另建自动化替代。

执行不得扩大对外发送、花费、删除或服务控制权限。无需再对便单登录、补写或同步。
